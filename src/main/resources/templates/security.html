Security

Last updated August 2026

Found a vulnerability? Please report it privately rather than posting it publicly, and give us a reasonable window to fix it before disclosing. Details in Reporting a vulnerability below.

How accounts are protected

  • Passwords are never stored. We store a one-way hash, so even with database access your password cannot be read back.
  • Email verification. New accounts must confirm their email address before they become active, so an account can't be created and used in your name.
  • Encrypted in transit. The whole site is served over HTTPS with a certificate issued by Amazon Certificate Manager, with HSTS enabled.
  • Session handling. Sessions are held server-side in Redis, not in the cookie itself, and the session cookie is HttpOnly so page scripts can't read it.
  • CSRF protection. State-changing form submissions carry a per-session anti-forgery token.

How your content is protected

  • Ownership is enforced on the server. Editing or deleting a post, Short, or comment is checked against the logged-in user on every request — not just hidden in the interface. A request sent directly to the endpoint by someone else is rejected.
  • Drafts are private. An unpublished post or Short is never returned in any feed, profile, or search result belonging to another user.
  • Database isolation. The database is not publicly reachable; it accepts connections only from inside the application's own private network.
  • Scoped upload permissions. The application can write uploads only to the specific storage prefixes it needs, and nothing else.

What we don't do yet

Being straight about the gaps is more useful than a list that implies more than is true:

  • There is no two-factor authentication yet.
  • There is no formal bug-bounty programme — reports are handled directly, and gratefully.
  • Media attached to published content is served from public URLs. Anyone with the link can view it, so treat anything you publish as public.

Reporting a vulnerability

If you believe you've found a security issue, please email bodhsea@gmail.com (subject line starting "Security") with:

  • What the issue is and roughly how severe you think it is
  • Steps to reproduce it, ideally with a specific request or URL
  • Whether you've disclosed it anywhere else

Please don't run automated scanners against the live service, access or modify other people's accounts or data, or degrade the service for other users while testing. We'll acknowledge your report, keep you updated while we work on it, and credit you if you'd like.

Something else wrong?

For abuse reports, account issues, or anything that isn't a security vulnerability, use the contact page instead.
